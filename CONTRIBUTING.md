# Contributing to Gutter

Thanks for helping out!

## Development

```sh
./build.sh --install
```

- Source lives in `Sources/Gutter/`, grouped by area:
  - `App/`: startup (`main.swift`), persisted settings (`Preferences.swift`), the global
    shortcut (`HotKey.swift`), update checks through Sparkle (`Updater.swift`, inactive in
    `swift run` builds, which have no `SUFeedURL`), the hidden main menu that makes ⌘, and ⌘W
    work in Settings (`MainMenu.swift`), and version, icon and login item helpers (`AppInfo.swift`)
  - `Windows/`: Accessibility observers and window fitting (`WindowManager.swift`)
  - `MenuBar/`: the menu bar icon and right-click menu (`StatusItemController.swift`), the glass
    panel it opens (`GlassPanel.swift`) and the panel's content (`MenuView.swift`)
  - `Settings/`: the Settings window (⌘,) and its content
  - `UI/`: the parts the panel and Settings share: glass rows and switches (`GlassRows.swift`),
    the capsule picker and buttons (`CapsuleControls.swift`), and the display preview
    (`LayoutPreview.swift`)
  - `Debug/`: `--snapshot`, `--panel-test` and `--menu-test`, compiled into debug builds only
- `Sources/GutterKit/` holds the window-fitting math (margins, coordinates, which display a
  window is on, where it goes) with no AppKit state, so it can be unit tested. Put new geometry
  there, not in `WindowManager.swift`.
- The app target builds in Swift 6 mode with the main actor as its default isolation, since it's
  all UI. Accessibility, Carbon and notification callbacks already arrive on the main thread and
  enter the main actor with `MainActor.assumeIsolated`. Mark slow work `nonisolated` and run it off
  the main thread, like the wallpaper thumbnail in `LayoutPreview.swift`.
- Releases publish an `appcast.xml` (written by `scripts/appcast.sh`) that Sparkle reads from
  the latest release. It's signed with the EdDSA key in the `SPARKLE_PRIVATE_KEY` secret; the
  maintainer keeps a copy in the login keychain (`generate_keys --account gutter`). Without that
  key, existing installs can't be updated, so don't lose it.
- Releases also update the Homebrew cask in
  [jleitaom/homebrew-tap](https://github.com/jleitaom/homebrew-tap) (written by `scripts/cask.sh`),
  using a deploy key that can only write to that repo (the `TAP_DEPLOY_KEY` secret).
- The app icon is generated by `scripts/make-icon.swift`; edit and re-run it instead of editing the `.icns`.
- Ad-hoc builds need Accessibility access granted again after every rebuild. A self-signed
  certificate named `Gutter Self-Signed` in your keychain avoids that; `build.sh` uses it when
  it finds one (see the README).
- Check panel changes without the menu bar: `swift run Gutter --snapshot out.png [--dark]` renders it
  to an image, and `swift run Gutter --panel-test` opens the real panel and checks its size, and
  `swift run Gutter --menu-test` prints the right-click menu.

## Tests

```sh
swift test
```

Unit tests for `GutterKit` live in `Tests/GutterKitTests/` and use Swift Testing (Xcode 26 or
later). They're table tests: to cover a new display layout or margin case, add a row. CI runs
them on every PR, along with `--menu-test` and the panel snapshots (download them from the run's
artifacts to review design changes).

## Before a release

Window behavior depends on real apps and displays, so check these by hand with
`./build.sh --install`:

- [ ] With Stage Manager on, a new Finder window and a new Safari window land next to the strip.
- [ ] With Stage Manager off and "Only with Stage Manager" on, new windows are left alone.
- [ ] Moving a window to another display fits it to that display's gap.
- [ ] ⌃⌥⌘F fits the frontmost window; "Fit all windows" reports a count.
- [ ] An app in "Never resize" is left alone.
- [ ] With an app paused (`kill -STOP <pid>`), "Fit all windows" returns within a second and the
      panel stays responsive (`kill -CONT <pid>` afterwards).
- [ ] `swift run Gutter --panel-test` passes with every display connected.

## Reporting bugs

Window behavior varies a lot between apps. When reporting a problem, include:

- macOS version and display setup (number of monitors, resolutions)
- The app whose windows misbehave, and its version
- What you expected vs. what happened

## Pull requests

- Keep changes focused; one feature or fix per PR.
- Match the existing code style.
- Make sure `./build.sh` and `swift test` succeed; CI runs both on every PR.
- Add or update a test in `Tests/GutterKitTests/` when you change how windows are fitted.
- Add a line to `CHANGELOG.md` under **Unreleased**.
